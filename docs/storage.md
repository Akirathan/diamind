# Storage

- All text nodes are kept in memory as plain objects, in the renderer process.
- SQLite is the persistent storage. It is read once at startup and then only receives writes.
- Attachments are files on disk, never loaded into memory unless visible.
- Only one window and one app instance (`app.requestSingleInstanceLock()`).

## Why not Yjs

- Measured by the Yjs memory benchmark in [PR #1](https://github.com/Akirathan/diamind/pull/1) (closed, not merged).
- For 500k nodes, Yjs needs ~3 GB of heap and ~7 s to load. Plain objects need ~160 MB and ~0.3 s.
- Sync between devices is not a goal now. If needed later, sync the commands (see below), not a CRDT of the whole outline.

## Architecture

```
Renderer process (React)                Main process (Node.js)
┌─────────────────────────────┐         ┌──────────────────────────┐
│ OutlineStore (plain objects)│         │ Persistence              │
│  - nodes: Map<id, Node>     │  IPC    │  - drizzle-orm           │
│  - children: Map<id, id[]>  │ ──────► │  - better-sqlite3        │
│  - commands, undo stack     │ changes │  - one transaction/batch │
└─────────────────────────────┘         └──────────────────────────┘
         ▲                                          │
         └──────────── all rows at startup ─────────┘
```

- The renderer owns the in-memory model. Typing, search and filter never wait for IPC.
- The main process owns the database file. `better-sqlite3` is a native module, so it runs only in the main process.
- SQLite is accessed via [drizzle](https://orm.drizzle.team/) (`drizzle-orm/better-sqlite3`).
  - The SQL schema is in `src/main/db/schema.ts`. The renderer does not see it.
  - The row types (`Node`, `NodeUiState`, `ChangeSet`) are in `src/shared/outline` and shared by both processes.
  - Migrations are generated by `drizzle-kit` and applied at startup with `migrate()`.

## Schema

```
nodes
  id            TEXT PRIMARY KEY
  parent_id     TEXT          -- NULL for the root
  sort_key      TEXT NOT NULL -- fractional index, order between siblings
  type          TEXT NOT NULL -- 'text' | 'attachment'
  format        TEXT NOT NULL -- 'bullet' | 'paragraph' | 'h1' | 'h2' | 'h3' | 'divider'
  text          TEXT NOT NULL DEFAULT ''
  note          TEXT NOT NULL DEFAULT ''
  completed_at  INTEGER       -- NULL if not completed
  attributes    TEXT          -- JSON object, NULL if the node has no attributes
  attachment_id TEXT
  created_at    INTEGER NOT NULL
  modified_at   INTEGER NOT NULL

attachments
  id     TEXT PRIMARY KEY
  path   TEXT NOT NULL  -- relative to ~/.local/share/diamind/attachments/
  mime   TEXT NOT NULL
  size   INTEGER NOT NULL
  sha256 TEXT NOT NULL

node_ui_state   -- per device, not part of the outline
  node_id    TEXT PRIMARY KEY
  collapsed  INTEGER NOT NULL DEFAULT 0
  scroll_top INTEGER        -- scroll position when zoomed into this node

app_state       -- per device
  key   TEXT PRIMARY KEY   -- e.g. 'zoomedNodeId', 'navigationHistory', 'showCompleted'
  value TEXT NOT NULL      -- JSON
```

- The tree is stored by `parent_id`. The depth (indentation) is derived from the chain of parents, never stored.
  - Indent, unindent and move change one row only.
- `sort_key` is a fractional index (e.g. `fractional-indexing` library).
  - Inserting between two siblings creates a key between their keys. Siblings are not renumbered.
- Collapse state and scroll position are UI state, stored in `node_ui_state`, not in `nodes`.
- No foreign keys and no index on `parent_id`.
  - The in-memory model is the source of truth. A foreign key could reject a whole batch of changes.
  - All rows are read at startup, so no query needs the index.

## In-memory model

```ts
nodes: Map<string, Node>;
children: Map<string | null, string[]>; // sorted by sortKey
uiState: Map<string, NodeUiState>;
```

- `Node.attributes` is `undefined` for nodes without attributes, to save memory.

- `children` is not stored. It is built at startup from `parentId` and `sortKey` (~80 ms for 500k nodes).

## Commands

- The UI never mutates a node directly. Every change is a command:
  - `insertNode(parentId, afterId, format)`
  - `setText(id, text)`
  - `setFormat(id, format)`
  - `indent(id)`, `unindent(id)`
  - `move(id, newParentId, afterId)`
  - `deleteNode(id)` - deletes the whole subtree
  - `setCollapsed(id, collapsed)`
  - `setNote(id, note)`
  - `setCompleted(ids, completed)`
  - `setAttribute(id, key, value)`, `removeAttribute(id, key)`
- A command:
  1. Validates the rules of the [data model](data-model.md), e.g. two empty siblings, indentation only by +-1.
  2. Mutates the in-memory model.
  3. Returns a _change set_ of the changed rows, per table (`nodes`, `uiState`): `{ upsert, delete, before }`.
     - `before` holds the previous version of every changed or deleted row.
  4. Notifies the subscribers of the store with the change set: React, the undo history and the write queue.
- An invalid command throws an `OutlineError` and changes nothing.
- Commands are plain TypeScript, unit tested without Electron and SQLite.

## Write path

1. The renderer puts changed rows into a queue. A newer change of the same row replaces the older one.
2. ~300 ms after the last change, the queue is sent to the main process via IPC.
3. The main process writes the whole batch in one SQLite transaction.
4. The queue is also flushed immediately on window blur and on app quit.

- SQLite settings: `journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`.
- A crash may lose up to the last ~300 ms of changes. This is acceptable.
- A crash never corrupts the database (WAL).

## Undo / redo

- The undo stack is in memory only. It is empty after restart.
- One undo step can contain several commands, e.g. indenting multiple selected nodes.
- `UndoHistory` subscribes to the store. For each changed row it keeps the version before and after the change.
  - Undo and redo restore these exact rows, as a normal change set. The write path saves it like any other change.
- `transaction()` groups several commands into one step.
  - It is atomic. If a command throws, all commands of the transaction are undone.
- Consecutive `setText` of the same node merge into one step until a pause (1 s) or a cursor move. The same for `setNote`.
  - `setText` and `setNote` do not merge with each other.
- The stack keeps the last 1000 steps.

## Startup

1. The main process opens the database and applies migrations.
2. The main process reads all rows of `nodes` and `node_ui_state` and sends them to the renderer.
3. The renderer builds the in-memory model and shows the last zoomed node from `app_state`.
   - For an empty database, the store creates the global root. `OutlineStore.load()` returns it as a change set, which must be saved like any other change. Otherwise, each start creates a root with a different id.

- Target: under 1 s for 500k nodes. Measured: ~0.6 s until the renderer has the rows, ~0.25 s of it is the read in the main process.
- `loadOutline()` returns JSON text (`OutlineJson`), not objects. The renderer parses it with `parseOutlineJson()`.
  - SQLite builds the JSON of each row. Nodes are sent in chunks of 100k rows.
  - Cloning 500k objects over IPC takes ~1.5 s. A few large strings are much faster.
